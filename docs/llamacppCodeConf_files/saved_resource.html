llamacppCodeConf

A desktop manager for local AI model serving — it finds the models on a machine, serves them through one hot-swapping server, measures what each one can actually do on the available hardware, and keeps client applications configured with numbers that are true.

The problem it addresses

Running large language models locally is attractive — private, free per-token, offline — but the tooling around it punishes non-experts:

  • Models scatter. Ollama keeps them in a content-addressed blob store, HuggingFace tools keep a revision-pointer cache, manual downloads land wherever. A machine can hold 200+ GB of models with no single answer to “what do I have, and is it usable?” During development, the app’s own scanner surfaced a 20 GB model the owner didn’t know was there — and one that was on disk but unreachable because a cache pointer had silently moved.
  • Configuration runs on folklore. Client apps need each model’s context window. The number in the model file is the training figure; what actually fits after GPU memory allocation is routinely a third of that. Configs written from file headers cause silent truncation and mid-session failures that are miserable to debug.
  • The expertise barrier is real. llama.cpp exposes dozens of flags with meaningful performance consequences. Most users never find them; the knowledge lives in forum threads.
  • Version skew breaks things cryptically. Model formats evolve faster than installed binaries; a failed load reports an error deep in a server log, actionable only if you already know the answer.

The approach: measured, not guessed

The core design decision: the app never writes a number it hasn’t measured. Loading a model is measuring it — the app records the context size the server actually settled on for this machine and probes whether the model produces well-formed tool calls, then writes client configuration from those measurements, with a small safety margin. Measurements are fingerprinted against the server build, GPU set, and per-model flags, so they refresh automatically when anything relevant changes; stale numbers are labeled stale rather than silently trusted.

The same philosophy extends to diagnostics. Every unavailable model has a “Why?” button giving a plain-language cause, the single relevant error line as evidence, and remedy buttons — because “see the logs” is not an answer a general user can act on. A built-in Build Advisor compares the installed llama.cpp against its source checkout and upstream, reports in outcomes (“rebuilding would unlock 3 models you own”) rather than compiler flags, and runs the guided rebuild itself. In live use it correctly distinguished “your checkout was updated but never rebuilt” from “you need to pull” — and after the rebuild, re-measurement confirmed one previously unloadable model working while honestly reclassifying three others as incompatible-by-design, updating its own advice accordingly.

What it does today

  • Discovers llama.cpp installations (version, GPU visibility per binary) and every GGUF model across user directories, the Ollama store, and the HuggingFace cache, deduplicated by file identity.
  • Runs llama-server in router mode: one server, all models, on-demand hot-swap.
  • Generates server configuration with performance defaults measured on real hardware; per-model overrides survive regeneration and open pre-filled with the optimized values, with a reset-to-optimized escape hatch.
  • Detects per-model capabilities from the files themselves — vision components (paired automatically), multi-token-prediction layers, embedding architectures — and configures serving accordingly.
  • Syncs the OpenCode coding agent’s config through a comment-preserving JSONC editor: hand edits survive, removals are reversible comment-outs, every write gets a numbered backup with one-click restore.
  • Offers a Connections panel for any other OpenAI-compatible app: base URL, the measured model list, copy-paste client snippets.
  • Coexists safely with other tools: a server it didn’t start is observed, never signaled; model files are never deleted by the app, period.

Engineering notes

  • Architecture: a headless, fully-testable core under a thin GUI shell; the same engine drives the desktop app and a scriptable CLI.
  • Verify before building: the project began with a spike day validating every load-bearing assumption against the real server binary before application code depended on it; findings are documented in the repository.
  • Bugs found by use, fixed at the root: live testing surfaced four identity/truth bugs — including a quantization label the model file itself misstated, confirmed by reading the tensor table directly. Each fix removed the class of error (a single source of truth for naming) rather than patching the instance, with a regression test citing the incident.
  • Safety invariants held throughout: never touch a process the app didn’t start (ownership handshakes robust to PID recycling); never destroy user data (comment-out over delete, backup before write, refuse to overwrite).
  • Built in Rust with a minimal dependency footprint, developed in an AI-pair-programming workflow with design decisions, testing discipline, and the roadmap maintained as first-class artifacts in the repo.

Current state, honestly

Working daily on its development machine (Linux, single NVIDIA GPU), where it manages 15+ models across three stores and keeps two client apps configured. Limitations worth stating: Linux-only today; multi-GPU support is designed in (GPU state is a list everywhere) but untested on real multi-GPU hardware; ROCm build support is implemented against documentation and simulated tests, not yet validated on AMD hardware; and it is a personal-scale project — one machine, one primary user — not yet hardened by a wider install base.

Planned next: a performance lab (benchmark-verified A/B of configuration changes, speculative-decoding trials) and a sibling project for model inventory and backup with content-hash identity.
